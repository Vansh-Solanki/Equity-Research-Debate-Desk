## One-line summary

Two AI analyst agents (Bull and Bear) debate a company's real SEC filing using retrieved, fact-checked evidence, a Judge agent scores the debate and writes a memo, and an optional deep-dive mode spawns section-specific sub-agents on demand. Built entirely on free tools, no paid subscriptions.

## Architecture (locked in)

```
Data sources (SEC EDGAR, yfinance, news RSS)
        |
MCP tool layer (get_filing, get_price, get_news)
        |
RAG index (chunk -> embed -> Chroma -> cross-encoder rerank)
        |
Agent crew (Bull, Bear, Judge — CrewAI + Groq)
        |-- Deep-dive spawner (sub-agent per filing section, on demand)
        |
Output layer (memo, Streamlit UI, Langfuse/local logging)
```

Deployment layer (added later, also locked in):
```
Browser -> Streamlit frontend -> FastAPI backend -> Redis job queue -> Worker pool
(worker pool runs the agent crew, calls Groq + Chroma, writes results back)
Hosted as a Docker container on Hugging Face Spaces (free)
```

## Key design decisions log

- **Debate turn order:** Fixed (Bull always first), implemented as an ordered list (`speaking_order = [bull_agent, bear_agent]`) so randomizing later is a one-line change if ever wanted. All logging/labeling is by agent name, never by position.
- **Independent research:** Bull and Bear run separate retrieval queries and write opening statements without seeing each other's statement. From round 2 onward, each agent reads the full transcript and must directly engage with the other's specific points.
- **Deep-dive trigger:** User-initiated only, via one button per filing section (dynamically generated from however many sections that specific filing has), not automatic. Clicking a button spawns exactly one sub-agent for that section; already-dived sections are cached, not rerun.
- **Hallucination checking:** One shared evaluation pipeline (claim extraction -> retrieval -> cross-encoder rerank -> NLI entailment check) applied uniformly to Bull, Bear, the Judge, and deep-dive sub-agents. No agent is exempt or self-certifying.
- **Scope boundary:** Confirmed this project does NOT cover merger and acquisition analysis (single-company research only, not deal/comparison scenarios).
- **Vector DB:** Chroma chosen over FAISS/Qdrant/Weaviate/Milvus/LanceDB/pgvector/Annoy/Redis-vector — best balance of ease of use, metadata filtering, and appropriate scale for this project.
- **Deployment concurrency:** Queue-worker pattern (Redis + worker pool) chosen over a naive single-process Streamlit app specifically to support multiple concurrent users without blocking or session collisions. Acknowledged limitation: real throughput is capped by Groq's free-tier rate limit, not by the architecture itself.

- **Groq model choice:** `llama-3.1-8b-instant` (originally assumed in spec.md) is no longer available on the free-tier account as of Aug 2026. Switched to `openai/gpt-oss-20b`, confirmed working with 1000 requests/day and 8000 tokens/min free-tier limits. Re-check `client.models.list()` if agents start hitting 404s later — Groq's free model lineup changes.

- **MCP SDK version:** Installing `crewai` in Phase 3 pinned `mcp` back down to v1.28.1 (from the v2.1.1 that Phase 2 was built against), which removed `mcp.server.mcpserver.MCPServer`. `mcp_server/server.py` now uses `from mcp.server.fastmcp import FastMCP` instead — decorator usage (`@mcp.tool()`) is unchanged. If `mcp` gets upgraded again later, re-check this import.
- **News source:** Spec suggested free RSS feeds generically; implemented against Google News RSS (`news.google.com/rss/search`) since it needs no API key and works for arbitrary company names, not just tickers.
- **SEC EDGAR user agent:** Set to `Equity Research Debate Desk vsolanki4565@gmail.com` in `.env` — SEC blocks requests with generic/placeholder user agents.
- **Filing text extraction:** Added `beautifulsoup4` (not in original spec's requirements.txt draft) to strip HTML from 10-K documents into plain text for later chunking in Phase 5. Raw text capped at 3M chars as a safety limit.

- **Phase 3 — CrewAI version and Groq quirks (crewai 1.15.18):**
  - `crewai`'s generic litellm-fallback `LLM` class (used for any model without a native provider integration, which includes Groq) stamps every message with a `cache_breakpoint` field intended for Anthropic-style prompt caching, but never strips it for providers that don't understand it. Groq's OpenAI-compatible endpoint strictly rejects unknown message fields and 400s on every call. Worked around in `agents/llm.py` by monkeypatching `crewai.llms.cache.mark_cache_breakpoint` to a no-op — both crewai executors re-import that name locally on each call, so patching the source module's attribute is enough. Revisit if crewai ships a real fix upstream.
  - `crewai` requires `litellm` installed separately as of 1.15.18 (`pip install litellm`) for any model that isn't one of its natively-integrated providers (openai/anthropic/azure/bedrock/gemini/etc.) — added to `requirements.txt`.
  - Groq's free tier (8000 tokens/minute) is tight enough that a ReAct-style agent loop calling multiple tools (get_filing + get_price + get_news) in one task run reliably blows the budget, since each turn resends the full growing conversation history. Fixed by: (1) trimming what each tool returns before it reaches the agent's context (`agents/tools.py` — filing text capped at 2500 chars starting from the actual cover page rather than the XBRL tag-data preamble that precedes it in the stripped HTML, price history capped to the last 5 points, news summaries capped to 200 chars), (2) `max_iter=2` per agent (one tool-call turn, one final-answer turn), (3) each Phase 3 task instructs the agent to call `get_filing` only, skipping `get_price`/`get_news`, and (4) `agents/llm.py`'s `run_with_rate_limit_backoff` retries a `RateLimitError` by sleeping the exact wait time Groq's error message reports. This is a real free-tier constraint, not a one-off bug — worth revisiting once Phase 5's RAG retrieval replaces raw tool dumps with much smaller retrieved chunks, and again in Phase 4 when the debate loop needs multiple sequential agent turns.
  - `get_filing`'s stripped HTML started with a long block of inline-XBRL tag data (fund identifiers, GAAP taxonomy refs) with no prose in it before the actual filing cover page began — for AAPL/MSFT/TSLA the real text started 14k-34k characters in. Initially worked around at the call site (`agents/tools.py` searched for the cover-page marker and truncated from there); **later fixed at the source** in `mcp_server/tools/get_filing.py` — see the "Known issues" entry below for the real fix.

- **Phase 4 — debate loop and Judge agent:**
  - `orchestration/debate_loop.py` holds `speaking_order = [bull_agent, bear_agent]` as the ordered-list pattern spec.md requires; round 1 calls each side's `run_opening_statement` (independent, as in Phase 3), rounds 2+ call `run_rebuttal(company, transcript_text)` which feeds the full transcript-so-far back in and instructs each side to engage the opponent's most recent specific point before adding anything new.
  - `agents/judge_agent.py` is new: reads the finished transcript and scores `stronger_side` / `claims_checked` / `claims_unsupported` / `memo`. Deliberately does its own reading rather than calling any evidence-retrieval tool — real claim-level verification (extraction -> retrieval -> entailment) is Phase 6's shared pipeline, applied uniformly to Bull, Bear, Judge, and deep-dive sub-agents alike; the Judge is not exempt from that later.
  - **New crewai/Groq bug found in Phase 4: a zero-tools agent can still 400.** Giving `run_rebuttal`/the Judge `tools=[]` (the natural way to say "don't call tools") triggers a different code path in crewai's executor (`call_llm_and_parse`, used when `self.original_tools` is empty) that still sends `tool_choice: "none"` to Groq — and `openai/gpt-oss-20b` sometimes emits a tool call anyway (observed calling a hallucinated `browser.get_filing`, and separately a real `get_filing` with a bogus extra arg), which Groq validates strictly and rejects with a 400 (`"Tool choice is none, but model called a tool"`). Worked around by keeping every agent's real tools attached (`tools=ALL_TOOLS`) always, and telling it not to call them via the task description instead — plus `agents/llm.py`'s `run_with_rate_limit_backoff` now also retries this specific `BadRequestError`, since it's model non-determinism (a retry usually doesn't repeat the same errant tool call).
  - **`output_pydantic` costs an extra, unretried LLM call.** The Judge originally used `Task(output_pydantic=JudgeVerdict)` for structured output. crewai converts free text into the pydantic model via a second, separate LLM call (through the `instructor` library) when the model doesn't return native structured output — and that conversion call isn't covered by our `run_with_rate_limit_backoff` wrapper, so it fails hard on any rate limit. Replaced with a plain structured-text format (`STRONGER_SIDE: ...` / `CLAIMS_CHECKED: ...` / etc.) that the Judge is instructed to output and `agents/judge_agent.py`'s `_parse_verdict` parses with a regex — no extra LLM call, no extra failure point.
  - **Groq free tier has a daily cap too, not just per-minute.** `openai/gpt-oss-20b` on this account is capped at both 8000 tokens/minute *and* 200,000 tokens/day. Heavy same-day testing (this Phase 3 + Phase 4 session) ran the daily quota down to ~0 remaining — confirmed via a `RateLimitError` reporting "on tokens per day (TPD): Limit 200000, Used 199965". `run_with_rate_limit_backoff`'s retry-after parser only handled seconds ("Xs"), not the "Xm Y.Zs" format Groq uses for longer (daily-cap) waits, so it was retrying every ~15s against a 20+ minute wait and burning through all 6 attempts uselessly. Fixed: the parser now handles both formats, and any parsed wait over `MAX_SENSIBLE_WAIT_SECONDS` (90s) is treated as the daily cap and fails fast with a clear message instead of blocking or retrying futilely.
  - **Not yet re-verified after the last two fixes** (Judge's plain-text parser, the daily-cap fail-fast): the daily quota ran out before a fresh end-to-end run could confirm them together. The debate loop *was* fully verified end-to-end before those fixes (`scripts/test_phase4_debate.py` on AAPL — 3 rounds, every round-2+ statement named and rebutted a specific opponent claim, Judge produced a verdict), so the core mechanism is proven; re-run `python -m scripts.test_phase4_debate AAPL` once the daily quota resets to confirm the memo no longer truncates.
  - Also bumped `orchestration/debate_loop.py`'s `INTER_TURN_PAUSE_SECONDS` to 15s between agent turns, to spread requests out against the per-minute cap and reduce (not eliminate) how often the retry path is needed at all.
  - **Later fix (post-Phase-8, same debate-loop/Judge subsystem): the Judge used to write its memo blind to the very entailment data used to grade it.** `_entry()` already ran every Bull/Bear statement through `evaluation.pipeline.check_statement` turn by turn during the loop (wired in properly by Phase 6) — by the time the loop reached the Judge, `claim_details` already held every real entailment result for every claim. But the aggregation (`all_debate_claims` / counting unsupported) happened *after* `judge_agent.run_verdict()` returned, purely to silently overwrite the Judge's self-reported `claims_checked`/`claims_unsupported`. The Judge itself never saw this data — it wrote its memo from the transcript and retrieved excerpts alone, which could describe a different picture of the debate than the programmatically-measured counts backing it.
    - **Fix**: moved the aggregation (`all_debate_claims`, `unsupported_claims`) to before the `run_verdict()` call in `orchestration/debate_loop.py`, and pass both in as new required params. `claims_checked`/`claims_unsupported` are still set programmatically afterward from the same data, never trusted from the LLM's own output — that part of the design was already correct. What changed is that the memo's prose and the programmatic counts now describe the same underlying reality instead of being computed independently and only coincidentally agreeing.
    - `agents/judge_agent.py`'s `run_verdict(company, transcript_text, all_debate_claims, unsupported_claims)` builds a new prompt block from this: up to `MAX_UNSUPPORTED_CLAIMS_SHOWN` (10) unsupported/contradicted claims formatted as `[AGENT] "claim text" -> label` lines (sorted by ascending confidence, so a cap still surfaces the most anomalous claims first, not an arbitrary slice) — lets the memo cite specifics ("Bull's claim about X was unsupported") instead of just restating a count. Capped because one real test run had 25 unsupported claims, which would otherwise blow the token budget.
    - **Deliberately kept both grounding sources, not replaced one with the other**: retrieved filing excerpts (Phase 5-wiring fix, above) give the Judge raw filing language to quote for texture; the pre-computed entailment data gives it the actual verified support/contradiction verdict per claim, which excerpts alone don't provide (the Judge would still have to infer that itself by eyeballing the excerpt — the exact unreliable judgment call this fix removes). Dropping the excerpts would leave the Judge with labels but no ability to explain *why* a claim failed in its own prose; dropping the entailment data is the original bug. They're complementary, not redundant.
    - **Verified live** (`python -m scripts.test_phase8_dashboard AAPL`, real Groq run): the Judge's memo now explicitly names specific claims and explains why each side's evidence did or didn't hold up — *"The Bull's case is better supported: it cites factual data from the filing — net sales and operating expenses both rose 8%, R&D spend grew 10% to $34.6 billion, and Greater China sales fell 8% in 2023 — all corroborated by the excerpt. The Bear's arguments rely on interpretation or unverified claims, such as 'disciplined scaling without margin erosion' and a 2025 Greater China decline of 8%, which are not substantiated by the filing."* This is qualitatively different from before the fix (a generic score with no specific claim citations) and confirms the intended behavior. Judge groundedness also moved from 0% (the pre-fix run reported in Phase 8's write-up below) to 50% in this run — still a small sample, but a meaningful directional confirmation, not proof at scale.

- **Phase 5 — RAG index (Chroma):**
  - `rag/chunker.py`: fixed-window chunking with overlap (1000 chars / 200 overlap, snapped to word boundaries), sized to `all-MiniLM-L6-v2`'s 256-token truncation limit. Not the Item-N section-aware split — that's still Phase 7's `deep_dive/section_splitter.py`, run separately for deep-dive filtering. `chunk_filing()` takes a `get_filing()` data dict and returns records with deterministic ids (`{company}-{filing_type}-{section}-{chunk_index}`, no random component — see the id-collision bug below for why that matters) and metadata (company, filing_type, filed_date, source_url, section, chunk_index).
  - `rag/embedder.py`: local `sentence-transformers` (`all-MiniLM-L6-v2`), no API key, cached as a module-level singleton since loading the model is the slow part.
  - `rag/chroma_store.py`: one persistent Chroma collection per company (`filing_{TICKER}`), not one shared collection with a metadata filter — simple physical isolation, good enough for Phase 5's single-user testing. Phase 10's `orchestration/session.py` adds per-debate-session isolation on top of this later.
  - `rag/reranker.py`: cross-encoder (`cross-encoder/ms-marco-MiniLM-L-6-v2`) reranks Chroma's vector-similarity candidates — slower but more precise than bi-encoder similarity alone, run only over the small candidate set Chroma already narrowed down to.
  - `rag/retriever.py`: `index_company_filing(company, filing_type)` ties chunker+embedder+chroma_store together; `retrieve(query, company, top_k, candidate_k)` ties embedder+chroma_store+reranker together.
  - **Real bug found during acceptance testing: chunk ids had a random UUID suffix, silently breaking "upsert" idempotency.** `chunk_filing()` originally appended `uuid.uuid4().hex[:8]` to every chunk id "to guarantee uniqueness," which meant every call to `index_company_filing()` generated an entirely new set of ids — so `chroma_store.upsert_chunks()`'s upsert-by-id never actually overwrote a previous index, it just kept *adding* duplicate copies of the same filing's chunks (old text alongside new text) every time a company was re-indexed. This went unnoticed until the `get_filing.py` page-footer fix (below) was tested: the retrieval acceptance script re-indexed AAPL and still surfaced pre-fix chunk text containing the old footer noise, because the collection now held both pre-fix and post-fix chunks mixed together and Chroma had no way to know the old ones were stale. Fixed two ways: (1) chunk ids are now fully deterministic (company + filing_type + section + chunk_index, no random component), so a same-length re-index correctly overwrites via upsert; (2) `chroma_store.delete_filing_chunks()` is called before every `index_company_filing()` upsert regardless, since a *shorter* re-index (fewer chunks than before, e.g. after a text-cleaning fix) would still leave the old tail-end chunks orphaned even with deterministic ids. Local `chroma_data/` was wiped and rebuilt clean after this fix — anyone with a pre-existing local Chroma store from before this fix should do the same (`rm -rf chroma_data`) rather than trust upsert to have cleaned it up on its own.
  - **Second real bug, found in `get_filing.py`, surfaced while debugging the above:** AAPL's 10-K (not MSFT's or TSLA's — filer/template-specific) repeats a page-footer string ("`{Company Name}. | {Year} Form {Type} | {Page}`", e.g. "Apple Inc. | 2025 Form 10-K | 3") on every rendered page — confirmed 58 occurrences in one filing. It's pure page furniture with no content, but because it's near-identical across dozens of chunks, it actively hurt retrieval quality: a query landing near a page boundary would match on the shared footer text as easily as on the chunk's real content, pulling in the wrong chunk. Fixed in `mcp_server/tools/get_filing.py`'s new `_strip_page_footers()`, called after `_strip_html()`, using a regex built from the filing's own already-resolved company name (`re.escape(company_name) + r"\.?\s*\|\s*\d{4}\s*Form\s+[\w-]+\s*\|\s*\d+\b"`) so it only ever matches that filing's real footer, never guesses. Verified zero leftover matches on all 7 previously-tested filers (AAPL/MSFT/TSLA/RIOT/NVAX/BABA/TM) and zero regressions (MSFT/TSLA/etc. had 0 matches before and after, since they don't use this footer style).
  - **Acceptance methodology**: no hand-labeled test set exists yet (`evaluation/test_set.json` is Phase 6's job, for claim-level entailment, not retrieval). `scripts/test_phase5_retrieval.py` instead builds a reproducible smoke test from the filing itself — index it, sample chunks spread across the document, treat a snippet from partway through each as a "question," and check whether reranking correctly re-surfaces that exact source chunk in the top 3 out of the company's *entire* chunk set (258 for AAPL, 407 for MSFT). Had to add a distinctiveness filter (snippet must contain a digit or >= 2 proper-noun-like capitalized words) after discovering that a naive random-span sampler frequently landed on genuinely-duplicated legal boilerplate (10-K risk-factor paragraphs routinely close with the identical sentence "...could materially adversely affect the Company's business, reputation, results of operations, financial condition and stock price." verbatim, dozens of times) — no retriever can or should disambiguate between interchangeable instances of the same boilerplate sentence, so scoring those as failures was testing document repetitiveness, not retrieval quality. Final result: 10/10 on both AAPL and MSFT (acceptance bar is >= 8/10). **A later run scored 8/10 instead** — the two misses (Q1, Q8) both sampled a snippet starting/ending mid-word ("nal computers, tablets..." / "...comply with t"). **Misdiagnosed at the time as a chunk-boundary issue** (attributed to `rag/chunker.py`'s fixed-window chunking and used as a motivating symptom for the Phase 5 chunker rework below) — actually impossible even under the *old* chunker, which already snapped every chunk boundary to a word boundary (`text.rfind(" ", ...)`) and so never produced a chunk starting mid-word in the first place. The real cause, found and fixed much later: `evaluation/retrieval_metrics.py`'s `sample_test_questions` sampled its "question" snippet via a fixed `text[100:]` character cut with no word-boundary snap of its own — see the dedicated bug entry under the Phase 5 rework's "Verified live" results below for the fix. (The chunker rework was still correct and worth doing on its own merits — sentence-safe chunk boundaries are a real property worth having — it just wasn't the fix for *this specific* Q1/Q8 symptom, which had an unrelated cause in the test harness.)

  - **DONE — chunker reworked from fixed-window to structure-aware + sentence-safe chunking.** Root cause of the Q1/Q8 misses above: `chunk_text()`'s 1000-char/200-overlap windows were cut by raw character count, snapped only to the nearest *word* boundary, never a sentence or section boundary — sentences could land right at a chunk edge, and the 200-char overlap silently duplicated whichever sentence sat in that zone into two chunks with no record of it.
    - **Implemented — two-level chunking:**
      1. **Level 1 (section split):** `rag/chunker.py`'s `chunk_filing()` now calls `deep_dive/section_splitter.py`'s existing `split_sections(raw_text)` itself (locally imported inside the function to avoid a module-load cycle, since `section_splitter.py` itself imports `chunk_filing` — deferring the import to call time sidesteps it) whenever `section` isn't already given, splitting the filing into Item-N sections *before* chunking, so the main index is section-labeled for the first time (`metadata["section"]` now carries the real label instead of always `""`). When `section` *is* given (deep-dive's call pattern, already scoped to one section's text), `chunk_filing()` skips the split and only does level 2 on that text.
      2. **Level 2 (sentence-safe sub-chunking):** `chunk_text()` was fully rewritten — `_split_sentences()` splits on sentence-ending punctuation, and sentences are packed into ~1000-char (`CHUNK_SIZE_CHARS`) groups with 1 sentence (`OVERLAP_SENTENCES`) of overlap carried into the next chunk. A sentence is never split across two chunks; a chunk never crosses a section boundary. The one edge case with no sentence punctuation to split on (e.g. a flattened table row longer than `CHUNK_SIZE_CHARS` on its own) falls back to the original word-boundary window splitter (`_hard_split`), unchanged from Phase 5's original implementation.
      3. `chunk_filing()`'s output shape is unchanged (`{"id", "text", "metadata"}`) — confirmed nothing downstream needed touching to consume it.

- **`evaluation/pipeline.py`'s `_select_relevant_span()` can pick the wrong span when a chunk mentions two similarly-worded but distinct things close together.** Found while verifying the Phase 6 claim-extraction multi-fact-split fix (see Phase 6's write-up above): for the claim "Microsoft 365 Consumer cloud subscriber growth was 7% in fiscal 2026," `retrieve()` correctly surfaces the right chunk at rank 0 — it literally contains "Microsoft 365 Consumer subscriber growth of 7%" — but the same chunk also discusses "Microsoft 365 **Commercial**" cloud/seat growth a sentence earlier, and `_select_relevant_span()`'s embedding-similarity narrowing picked the Commercial span instead of the Consumer one, so the NLI classifier never saw the fact the claim was actually about and returned `not_enough_evidence` at full confidence. Confirmed on two real cases (msft-03, msft-06's second half after splitting). **Implemented (`KEYWORD_BOOST`), verified per the plan below — partial improvement, doesn't fully resolve the two known cases; see the follow-on finding after the plan.**

  - **Implemented: hybrid keyword-boosted span selection.** Root cause: `_select_relevant_span()` ranks candidate spans purely by embedding cosine similarity to the claim, with no signal for whether a span contains the *specific* distinctive word the claim is actually about — "Commercial" and "Consumer" are similar enough in surrounding phrasing and topic (same product, same kind of growth-percentage sentence) that the embedding model treats them as near-duplicates, and ties/near-ties get resolved by whichever span happens to score marginally higher, not by which one is factually about the right thing.
    - **Explicitly not a pure fallback ("try exact match, only use similarity if that fails").** A strict two-stage fallback breaks in both directions: most claims (e.g. "Apple's net sales rose 8%") have no single unique keyword to search for, so keyword-only matching would be too blunt to use as a first-pass filter; and even when a keyword does appear, it can appear in more than one span (e.g. both a "Consumer revenue" line and an unrelated "Consumer headcount" line), so keyword presence alone can't fully disambiguate either. Similarity still needs to do most of the work.
    - **Design: keyword presence as an additive boost on top of the existing similarity score, not a replacement for it or a separate stage.** `_select_relevant_span()`: after computing `scores` (renamed from `similarities`) as before, `_distinctive_keywords(claim)` extracts the claim's distinctive words (capitalized words past the first — same "not just because it's the sentence start" spirit `evaluation/retrieval_metrics.py`'s `_looks_distinctive` already uses for a different purpose), then any span containing one of those words as a literal substring gets `KEYWORD_BOOST = 0.1` added to its score before `argmax`. If no span contains a distinctive keyword, behavior is unchanged from before (pure similarity). `KEYWORD_BOOST`'s magnitude was picked to match `check_claim`'s own `TOP_RANK_BONUS` tie-break scale, not separately tuned — see the verification results below for why that wasn't revisited.
    - **Why this is lower-risk than the previously-reverted `SPAN_NEIGHBORS=2` attempt (see Phase 6 write-up above):** that fix widened *how much text* gets considered for every claim, which pulled in more unrelated noise across the board and measurably hurt F1 (0.72 -> 0.67). This fix doesn't widen the candidate pool at all — it only re-weights spans that are already being scored, and only when a literal keyword match exists, so claims with no distinctive keyword (the majority) are entirely unaffected and can't regress.

      2. ## Session — Sept 8: Judge faithfulness framework (Layer 2 / Layer 3 scoping)

**Context:** ran `scripts/diagnose_judge_claims` to finally do the diagnostic that open issue #1 above had flagged as not-yet-done (print every judge-labeled claim next to its source memo text, to distinguish "extractor misclassifying meta-commentary" from "Judge genuinely hallucinating").

**Result of the diagnostic — hypothesis confirmed, fix applied, but a new gap surfaced:**

- **Extractor fix confirmed working, zero regression.** The claim extractor was updated to recognize debate-commentary sentences ("Bull's claim... was flagged as unsupported") as meta-commentary rather than re-testable standalone facts. On the diagnostic memo: 7 spurious claims → 0. `scripts/test_phase6_evaluation.py` re-run afterward: byte-identical to the pre-fix baseline (F1 = 0.72, same precision/recall breakdown per label, same pass/fail on all 30 hand-labeled test claims) — confirms the fix is isolated to Judge-memo-style phrasing and doesn't touch Bull/Bear claim extraction at all, since the hand-labeled test set doesn't contain that phrasing pattern.
- **New problem exposed by the fix**: `dashboard.py`'s `compute_groundedness_by_agent()` groups claims by `claim["agent"]` and only includes an agent in the output if it has >= 1 claim. A well-written Judge memo built entirely around citing already-checked claims by name (exactly what the Phase 4 "later fix" — Judge sees entailment data before writing — was designed to produce) is now *entirely* meta-commentary, so it produces zero extractable claims. Result: the `judge` key doesn't report `0%`, it disappears from `by_agent` silently. Confirmed live on a Phase 8 dashboard run: before the fix, `judge: 0%` (misleadingly, since it *looked* like real evidence of hallucination); after the fix, no `judge` key at all. Two smaller, unrelated moves in the same run (`bear` groundedness 31% -> 59%, deep-dive lift -4% -> +2%) attributed to normal run-to-run LLM variance, not this change, since Bull/Bear extraction logic wasn't touched.
- **This is a real side effect, not a bug**, but it means Layer 1 (factual groundedness via the existing Phase 6 pipeline) genuinely cannot answer "is the Judge doing its job correctly" on its own anymore — it was never designed to check whether the Judge is *accurately representing the debate*, only whether it states new facts that are true of the filing. **Not yet fixed**: `dashboard.py` should report an explicit `judge: N/A (no new factual claims — memo was entirely debate commentary)` instead of silently dropping the key, so this reads as expected behavior rather than a missing/broken metric. Small, separate change, not done yet.

**Decision: split "is the Judge grounded" into three distinct, separately-measured layers**, since a single score can't distinguish these failure modes from each other:

1. **Layer 1 — Factual groundedness.** Did the Judge state new true facts about the company? Checked against the filing (existing Phase 6 pipeline: extract -> retrieve -> NLI entailment). **Already built.** Often reports nothing to check now, per the gap above.
2. **Layer 2 — Citation accuracy.** Did the Judge accurately describe what actually happened in the debate (which side said what, and what its real status was)? Checked against `all_debate_claims`/`unsupported_claims`, the real data `debate_loop.py` already computes and hands to the Judge before it writes, **not** against the filing (the filing can't confirm or deny a fact about *this debate run*). **Not built.** Deferred — see below.
3. **Layer 3 — Verdict consistency.** Does `stronger_side` (bull/bear/tie) actually follow from the real claim data, or does the Judge's conclusion contradict its own evidence? Checked by comparing `stronger_side` against an objective per-side support-rate computed from `all_debate_claims`. **Not built.** Chosen to build first.

**Design intent behind the split**, consistent with a principle already present elsewhere in the codebase (`debate_loop.py` already refuses to trust the Judge's self-reported `claims_checked`/`claims_unsupported` and overwrites them programmatically): don't trust the Judge's own account of the debate or its own reasoning, verify both against the real data that was already computed. Layers 2 and 3 extend that same "don't trust, verify" logic to the Judge's prose and its final decision, not just its two summary numbers.

**Deliberately kept as deterministic checks, not a second LLM-as-judge call.** Confirmed in this session that the project currently uses LLM-as-judge in exactly one place (`evaluation/engagement_scorer.py`'s Phase 8 debate-engagement rubric) — everywhere else that checks correctness (Phase 6 entailment, Phase 5 retrieval, Judge-accuracy F1 against the hand-labeled set) deliberately avoids it in favor of a local NLI model, retrieval mechanics, or human labels. Layers 2 and 3 will follow that same pattern: string/data matching against `all_debate_claims` for Layer 2, arithmetic on per-side support rates for Layer 3, no new LLM call introduced to grade the Judge's LLM output.

**Build order decided: Layer 3 before Layer 2.**
- Layer 3 is pure arithmetic over data already sitting in memory (`all_debate_claims`) — count each side's supported vs. unsupported/contradicted claims, compute a support rate, compare it to `stronger_side`, flag disagreement past some threshold (threshold not yet chosen — needs eyeballing a few real runs, since close calls, e.g. 55% vs 50%, shouldn't be flagged as inconsistent). No text matching, no fuzzy logic, fastest to get right.
- Layer 2 needs to fuzzy-match a Judge's paraphrase of a claim ("Bull's claim about the 66% liquid deferred-revenue buffer") back to the actual claim text in `all_debate_claims`, since the Judge won't quote verbatim. That matching strategy (keyword/number overlap vs. something stricter) isn't decided yet, which is why it's deferred rather than started in parallel.

**Layer 3 — DONE, built and verified live same session.**
- `evaluation/judge_faithfulness.py`: `check_verdict_consistency(stronger_side, all_debate_claims)` — filters `all_debate_claims` to `agent in ("bull", "bear")`, reuses `evaluation.metrics.groundedness_pct` (not reimplemented) as the per-side support-rate formula (simple supported/total, no weighting — the "possible refinement, not needed for a first version" from the original plan), compares the two rates, and only calls it a real disagreement past `DISAGREEMENT_THRESHOLD = 0.15` (15 points). A gap under that (e.g. 55%/50%) resolves `evidence_favors` to `"tie"` and is always `consistent=True` regardless of what the Judge said — a close debate genuinely can go either way. One side having zero checked claims (e.g. a query returned nothing) short-circuits to `consistent=True` with an explicit "insufficient data" reason rather than comparing a real rate against 0%. Returns `judge_said`/`evidence_favors`/both sides' rates and claim counts/`gap`/`consistent`/a human-readable `reason` — deliberately over-returns (the original plan's sketch was just `{evidence_favors, judge_said, consistent, gap}`) since the extra fields cost nothing and make the dashboard's printed line self-explanatory without cross-referencing this module.
  - Verified pure arithmetic correctness first with synthetic cases before spending any Groq budget on it: a clear-win case where the Judge agrees (consistent), the same case with the Judge picking the *worse*-supported side (correctly flagged inconsistent), a close 55%/50% case with the Judge picking either side or "tie" (all consistent, confirming the threshold does what it's supposed to), and a zero-claims-on-one-side case (consistent, correct reason).
- **Threshold (`DISAGREEMENT_THRESHOLD = 0.15`) is a first-pass choice, not swept**, same honest caveat as `evaluation/pipeline.py`'s tuned constants — picked to comfortably clear "55%/50% shouldn't flag" from the original design note while still catching a real blowout (the synthetic 80%/20% case). Only one real debate run's data point exists so far (below); revisit if real runs start landing borderline right around 15%.
- **Wired into `evaluation/dashboard.py`** as a 7th, separate dashboard key (`verdict_consistency`) — not blended into `groundedness_by_agent`'s `judge` entry, per the original design intent (Layer 1 checks new stated facts, Layer 3 checks the final conclusion; conflating them would hide which one failed). `scripts/test_phase8_dashboard.py` prints it as a new "=== 7. Verdict consistency ===" section.
- **Also fixed the smaller side-gap flagged above**, same session: `compute_groundedness_by_agent` now takes an `expected_agents=("bull", "bear", "judge")` param and always includes all three keys, using `None` (not 0.0, and not a missing key) when an agent contributed zero checkable claims. `scripts/test_phase8_dashboard.py` prints `None` as `"N/A (no new factual claims — statement was entirely debate commentary or empty)"` instead of the value silently disappearing from the printed table.
- **Verified live** (`python -m scripts.test_phase8_dashboard AAPL`, real Groq run, 239.1s/14 calls): `groundedness_by_agent` returned `bull: 50%, bear: 47%, judge: 50%` — this particular memo mixed real new facts ("$112 billion net income," "66% deferred-revenue realization rate," both cited as supported/unsupported correctly) with debate commentary, unlike the earlier all-commentary diagnostic example, confirming the extractor fix handles both shapes of memo rather than only the one it was originally traced against. `verdict_consistency` returned `judge_said=tie, evidence_favors=tie` (bull 50% n=16, bear 47% n=17, gap=3%), `consistent=True` — a real, correctly-classified close call. `scripts/test_phase6_evaluation.py` re-confirmed F1 = 0.72 unchanged (this new module isn't in that script's path at all, run as a general regression sanity check).

**Layer 2 — DONE, built same session (matching strategy: extraction + embedding similarity, not string matching).**
- **Detecting citation sentences**: `evaluation/judge_faithfulness.py`'s `CITATION_SENTENCE_PATTERN` is a standalone regex (side word + a status-ish word like "flagged"/"unsupported"/"corroborated"/"cites" within ~150 chars), calibrated against real memo text from this session's own runs. **Explicitly not shared with `evaluation/claim_extractor.py`**, despite the original plan sketch assuming a reusable pattern — checked and confirmed that extractor's meta-commentary skip rule lives entirely inside its LLM prompt (`_PROMPT`'s "Also skip any sentence that reports on..." instruction), not a compiled regex, so there was nothing to import. A missed citation sentence here just means one fewer thing checked (not a false claim about the debate), so a looser, independently-tuned regex is an acceptable, lower-stakes design than the extractor's own skip logic needing to be precise.
- **{side, topic, status} extraction**: one small Groq call per detected citation sentence (`extract_citation_details`), using `litellm.completion()` directly with `reasoning_effort="low"` — same reasoning and same failure mode `evaluation/claim_extractor.py`'s docstring documents (GROQ_MODEL can burn its whole completion budget on hidden reasoning tokens on a longer/more complex input) — and wrapped in `agents.llm.run_with_rate_limit_backoff` under a new `"citation_extraction"` call-log label, so a live debate's latency breakdown (dashboard metric 5) can show this cost separately if Layer 2 is ever wired into a live run later.
- **Matching a citation's topic back to a real claim**: embedding cosine similarity via `rag/embedder.py`'s `embed_texts` (the same already-loaded `all-MiniLM-L6-v2` model `rag/retriever.py` and `evaluation/pipeline.py`'s span selection use, not a second model) — `match_to_real_claim` filters candidates to the claimed side when known, embeds the topic and every candidate claim's text, and picks the top cosine match.
- **Labeling-convention decision (was open, now resolved)**: "unsupported" in a Judge citation maps to *both* `not_enough_evidence` and `contradicted`, not just one — grounded directly in the existing codebase's own convention, not a new judgment call: `agents/judge_agent.py`'s `claims_block` prompt text already tells the Judge "X came back unsupported or lacking enough evidence" when handing it the pre-checked claims, treating those two labels as one bucket at the point the Judge is even given the data. `STATUS_EQUIVALENCE` encodes this; a citation naming a specific label ("contradicted") must still match that label exactly.
- **`MATCH_THRESHOLD`/`AMBIGUITY_MARGIN` — actually tuned against real numbers, not left as the received draft's untested 0.75 guess.** Built `evaluation/judge_citation_test_set.json` (8 entries: 6 pulled from real memo text seen in this session's own runs — Phase 4's write-up, the Phase 6 diagnostic, and both Sept-8 dashboard runs — plus 2 synthetic, one fabricated-citation case and one near-duplicate-phrasing ambiguous case) and `scripts/test_judge_citation_accuracy.py` (same shape as `scripts/test_phase6_evaluation.py`) to measure it.
